# Godot 4.7.1 capture and rendering interop

Related engine implementation and class documentation fetched directly from
Godot commit `a13da4feb8d8aefc283c3763d33a2f170a18d541`, resolved from
`4.7.1-stable` during this engagement. These sources describe GPU operations
and public interop boundaries, not measured capture performance.

## Attested details

1. Compatibility's desktop `texture_2d_get` binds `GL_PIXEL_PACK_BUFFER` to zero and calls `glGetTexImage` into CPU-owned storage. Its rendered textures do not use the non-render-target image-cache shortcut. [Readback implementation](https://github.com/godotengine/godot/blob/a13da4feb8d8aefc283c3763d33a2f170a18d541/drivers/gles3/storage/texture_storage.cpp#L1515-L1558).
2. Public `texture_drawable_create` and `texture_drawable_blit_rect` create sized targets and draw source textures into a destination rectangle. The GLES3 implementation attaches targets to a framebuffer, binds source textures, sets the destination viewport size and issues `glDrawArrays`. The default shader samples the whole source texture and uses `blend_mix`. [Public API](https://github.com/godotengine/godot/blob/a13da4feb8d8aefc283c3763d33a2f170a18d541/doc/classes/RenderingServer.xml#L3924-L3961), [bindings and destination size](https://github.com/godotengine/godot/blob/a13da4feb8d8aefc283c3763d33a2f170a18d541/drivers/gles3/storage/texture_storage.cpp#L1394-L1455), [draw](https://github.com/godotengine/godot/blob/a13da4feb8d8aefc283c3763d33a2f170a18d541/drivers/gles3/storage/texture_storage.cpp#L1488-L1497), [default shader](https://github.com/godotengine/godot/blob/a13da4feb8d8aefc283c3763d33a2f170a18d541/drivers/gles3/storage/texture_storage.cpp#L320-L339).
3. `viewport_get_texture` returns the viewport render target's texture RID. Public `texture_get_native_handle` is documented for third-party/GDExtension interop; its OpenGL value is a `GLuint`. Compatibility returns `texture->tex_id` directly. [Viewport RID](https://github.com/godotengine/godot/blob/a13da4feb8d8aefc283c3763d33a2f170a18d541/servers/rendering/renderer_viewport.cpp#L1227-L1232), [public handle contract](https://github.com/godotengine/godot/blob/a13da4feb8d8aefc283c3763d33a2f170a18d541/doc/classes/RenderingServer.xml#L3970-L3978), [native handle implementation](https://github.com/godotengine/godot/blob/a13da4feb8d8aefc283c3763d33a2f170a18d541/drivers/gles3/storage/texture_storage.cpp#L1972-L1977).
4. Both global and local RenderingDevice getters are documented as returning null with OpenGL. Compatibility's `texture_get_rd_texture` returns an empty RID. RenderingDevice's asynchronous texture getter promises later callback delivery of request-time data, but warns that bandwidth costs can remain prohibitive. [Global getter](https://github.com/godotengine/godot/blob/a13da4feb8d8aefc283c3763d33a2f170a18d541/doc/classes/RenderingServer.xml#L1663-L1668), [local getter](https://github.com/godotengine/godot/blob/a13da4feb8d8aefc283c3763d33a2f170a18d541/doc/classes/RenderingServer.xml#L1132-L1137), [empty RID](https://github.com/godotengine/godot/blob/a13da4feb8d8aefc283c3763d33a2f170a18d541/drivers/gles3/storage/texture_storage.cpp#L1968-L1970), [RD asynchronous getter](https://github.com/godotengine/godot/blob/a13da4feb8d8aefc283c3763d33a2f170a18d541/doc/classes/RenderingDevice.xml#L1191-L1199).
5. `call_on_render_thread` is documented for accessing rendering internals. Its implementation calls immediately when already on the rendering thread, otherwise queues the callable. It does not itself promise asynchronous GPU completion. [Documentation](https://github.com/godotengine/godot/blob/a13da4feb8d8aefc283c3763d33a2f170a18d541/doc/classes/RenderingServer.xml#L39-L44), [dispatch implementation](https://github.com/godotengine/godot/blob/a13da4feb8d8aefc283c3763d33a2f170a18d541/servers/rendering/rendering_server_default.h#L1216-L1223).
6. Godot's Compatibility initializer uses an `eglGetProcAddress` wrapper where available, distinguishes desktop GL from GLES loading, and falls back to GLAD's generic loaders. Its comment explicitly notes that different DisplayServers may obtain GL pointers differently. These are engine implementation details, not an exported GDExtension function-loader contract. [GL initialization](https://github.com/godotengine/godot/blob/a13da4feb8d8aefc283c3763d33a2f170a18d541/drivers/gles3/rasterizer_gles3.cpp#L232-L282).
